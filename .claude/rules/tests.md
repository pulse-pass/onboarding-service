# Tests

- Unit tests (JUnit 5 + Mockito + AssertJ) in `src/test/java/.../unit/`, mirroring the main packages: **one test class per production class**, never grouping several classes in one test.
- Test names `method_scenario_expectedResult`.
- External gateways (`infrastructure/gateways`) are unit-tested against `StubHttpServer`, a local HTTP server in the test package that records what it receives.
- Black-box integration tests with REST Assured against the service running in Docker Compose (no Testcontainers), in `src/test/java/.../integration/`: `BaseIntegrationTest` (URL, port and token from environment variables) and one class per route: `Test<Method><Action>` for routes that change something (e.g. `TestPostCreateOrganization`) and `Test<Method><Resource>` for GET routes, with no `Read` (e.g. `TestGetHealth`, `TestGetSession`). They run with `./mvnw test -Pintegration`; `./mvnw test` runs only the unit tests.
- Integration test classes have no constants other than the route URL (e.g. `private static final String POST_LEGAL_PERSONS = "/onboarding/legal_persons";`) and no helper methods of any visibility: each test declares its own data (names, documents, tokens), builds its own payload, makes its own call (REST Assured) and writes its own assertions inline, even when that repeats code across tests. Stateless tools (`JsonMapper`) are fine as instance fields, and `BaseIntegrationTest` keeps its shared constants and fields (URL, port, tokens). Unit tests may keep constants, `@BeforeEach` setup and private helpers.
- Request payloads in integration tests are declared in a single expression with `Map.of` and `List.of`, nested objects and lists included, never with `new HashMap<>()` plus `put`, `new ArrayList<>(List.of(...))` or JSON concatenated in a string. Above 10 entries use `Map.ofEntries(Map.entry(...), ...)`. `HashMap` is only for a test that needs an explicit `null` value or a mutable map. In TypeScript the equivalent is a typed object literal.
- Shared test helpers (`SetupTools`, `CpfGenerator`, `CnpjGenerator`, `MockTools`) live in `src/test/java/.../common/` and are the only reusable test code, plus the expectation templates in `src/test/resources/expectations/`. The no-constants rule applies to them too, except for URLs and paths in `SetupTools`; stateless tools (`JsonMapper`) are fine as fields, and `MockTools` keeps only its configurable address (see MockServer). `SetupTools` only creates prerequisites for **other** scopes (e.g. creating an organization to test the GET route); it does not hold payload builders.
- `SetupTools` methods (e.g. `createLegalPerson(ownerDocumentNumber)`) receive the data the test needs to control, register on the MockServer the expectations of the route they call, make the call and have a **single assertion, on the response status**, so a broken prerequisite fails at the setup line instead of later in the test. They clear the MockServer before registering their own expectations. A test that uses `SetupTools` calls it first and only then its own `MockTools.clearMocker()`, followed by its expectations (`SetupTools...`, `MockTools.clearMocker()`, `MockTools.addExpectation(...)`), so the setup expectations never answer the calls of the test. A test that needs a record that already exists creates it through `SetupTools`, never by relying on seed data from `database.sql` (the seeds are development fixtures, not test cases).
- REST Assured must be 6.x: Spring Boot 4 brings Groovy 5 and Jackson 3, which REST Assured 5.x cannot use.
- Integration tests are always run against the real compose (`./infrastructure/service-start.sh test` + `./mvnw test -Pintegration`) before a task is closed; unit tests with mocks do not catch persistence problems (lazy loading, constraints, schema validation).
- Each test generates its own data (UUIDs, random valid CPF and CNPJ); no teardown.
- Documents are generated by one class per document in `common/` (`CpfGenerator.generateCpf()`, `CnpjGenerator.generateCnpj()`); test helpers are not named `<Subject>Handlers`, which belongs to the production `common/` and would clash with it (same package).
- Every route has success and error tests; a 409 on duplicates proves the write when there is no GET route yet.
- No comments in test code (`//`, `/* */`, Javadoc).

## MockServer
- External services are played by the MockServer of the compose, driven by `MockTools` in `src/test/java/.../common/`: `clearMocker()`, `addExpectation(mockCode)`, `addExpectation(mockCode, pathParameters)`, `addExpectation(mockCode, pathParameters, expectationChanges)` and `retrieveRequests(method, path)`.
- Each external route has a default expectation in `src/test/resources/expectations/<api>/<method>-<name>.json`, in the MockServer format: `httpRequest` with `{param}` placeholders in the path and `httpResponse` with a realistic default body. Other responses of the same route are variants in their own file (`<method>-<name>_<variant>.json`, e.g. `keycloak/post-users_server_error.json`).
- `addExpectation` loads the template, sets `pathParameters` on the request and applies `expectationChanges` to the response: `payload` overrides keys of the body, `status_code` the status and `headers` the headers.
- Every integration test starts with `MockTools.clearMocker()` (right after its `SetupTools` calls, when it has any) and registers only the expectations it needs, with the values (ids, keys, tokens) declared in the test itself. No expectations in `@BeforeAll`, none shared between tests, and no `priority` or body matching to tell tests apart. Integration tests run sequentially because they share the MockServer.
- `MockTools` has no route-specific methods and no constants: paths live in the templates, and tests write the external paths inline in `retrieveRequests`.
