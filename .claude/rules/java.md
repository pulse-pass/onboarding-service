# Java code

## Structure
- Java 21, Spring Boot 4.x, Maven (no Gradle, no Lombok). Package `com.pulsepass.<service>`.
- Packages: `api` (controllers, schemas, responses, exceptions, validators), `application` (services, dtos/input), `domain` (entities, repositories, exceptions, `UnitOfWork`), `infrastructure/jpa` (JPA entities, `Jpa*Repository`, `*RepositoryImpl`, `JpaUnitOfWork`) and `common`.
- Code shared by every service is identical in all of them except for the package, tests included: `InternalRequestValidator` (`hasAdminRole`, `validateInternalTokenOrAdmin`, `validateSelectedAgentKey`) and its test, `DomainException`, the generic exceptions (`UnauthorizedInternalRequestException`, `MissingSelectedAgentKeyException`), `ErrorResponse`, `ExtraFieldErrorResponse`, `PaginatedResponse`/`PaginationResponse`, `UnitOfWork`/`JpaUnitOfWork` and `JsonHandlers`. A change to one of them (a rename, a new case, a new method) is applied to every repository that has it in the same task; before closing a task, diff these files across the repositories.
- Pure domain entity + JPA `*Entity` with `fromDomain`/`toDomain`; repository interface in the domain, implementation in `infrastructure/jpa`.
- JPA `*Entity` classes have only fields, constructors and `fromDomain`/`toDomain` — no getters/setters (Hibernate uses field access); this also keeps them from being flagged as duplicates of the domain entities.
- Inside entities (domain and JPA), always reference the object's own fields with `this.` (getters, `toDomain`, `toHistoryData`).
- Never read another entity's fields directly (e.g. `history.organization.name`); go through a method such as `toDomain()`, because lazy proxies only load on method calls and their fields stay empty.
- `common/` holds only general-purpose language helpers (string, JSON, document math), named `<Subject>Handlers` (`JsonHandlers`, `DocumentHandlers`) and placed directly in `common/`, without a `utils` subfolder. Framework concerns (HTTP clients, timeouts, Spring beans) never go to `common/`: prefer the Spring Boot configuration (properties and auto-configured beans such as `RestClient.Builder`); what is left stays in the class that uses it.
- Static factories follow `from<Source>` (`fromEntity`, `fromDomain`, `OrganizationHistory.fromOrganization`), not `create`.
- Logic that builds data from the entity itself (e.g. the history snapshot, `toHistoryData()`) belongs to the domain, not to the service.

## Method order
- Private methods always **before** public ones, in the order they are used.
- A log never receives a value that came straight from the request (path variable, query string, body), which Sonar flags as log injection (`javasecurity:S5145`) and which fails the quality gate. Log the value of the loaded entity (`organization.getOrganizationKey()`) instead, or leave it out when nothing was loaded yet.
- In the application layer, every `if` that changes the flow has a log as its first line: `logger.warn` when it refuses the request, `logger.info` when it takes another path.
- One `catch` per different handling: two `catch` blocks that do the same thing become a single `catch (Exception ex)`. A separate `catch` exists only when that exception has specific handling.
- Every gateway call in a service is inside a `try` with a `catch (Exception ex)`: any failure of the call is logged and becomes the domain exception of the operation, so it never leaves as a 500. A domain exception with a different meaning for the client (e.g. `InvalidCredentialsException`, `InvalidRefreshTokenException`) gets its own `catch` before it and is rethrown.
- `person.email` is unique across natural and legal persons (`person_email_unique`), because the payment provider refuses a repeated one: the company and its owner cannot share an email. The service checks it after the documents and answers 409 `ONB00010`.
- Nothing outside `infrastructure/` carries the name of an external provider, and domain exceptions and message keys describe the capability (`UserCreationException`, `OrganizationCreationException`), never who implements it.
- One gateway per external system, not per resource: all calls to a system go through the same class. The domain interface is named after the role or the internal service (`IdentityProviderGateway`, `OrganizationGateway`), and the implementation in `infrastructure/gateways/` after the system (`KeycloakIdentityProviderGateway`, `OrganizationServiceOrganizationGateway`).
- A gateway checks the transport failure, the response status and an empty body, and nothing else: it never validates the fields of a response one by one (`body.id() == null`), and it trusts the contract of the system it calls.
- When updating a loaded object, call `repository.save(object)` and keep using the same object: never capture the return in a variable such as `saved` or `failed`. The return is used only when creating, to get the generated data.
- Private methods only for real auxiliary steps used by several public methods or with a clear business name of their own (e.g. `saveLegalPerson`). The flow of a public method stays inline and linear, in the method itself: never extract its branches or its save, history and commit sequence to a private method (`approveOrganization`, `saveAndCommit`), even when lines repeat, and never to shorten the method.
- Lookups of domain tables by enumerator (`findByEnumerator(...).orElseThrow(...)`) stay inline in the public method, even when repeated, and are never extracted to a private method.
- In services and controllers, public methods go: create, then update, then get.
- Prefer separate, clear `if`s over compound `||` conditions when each case has its own meaning.

## Code
- No comments in code, configuration, scripts or Dockerfile (Javadoc included): names and structure must explain the code, and decisions go to the rules, the README or the task notes. The only exceptions are the version next to a workflow action pinned by SHA and generated or third-party files kept as they come (`mvnw`, `checkstyle.xml`).
- No defensive validation (e.g. checking that a value from the environment is not empty); `try/catch` only around the call that actually throws.
- Keep it simple: compare strings with `equals`, no `MessageDigest.isEqual` or similar tricks.
- `to*`/`from*` methods exist only in classes that represent data, converting themselves: `toDTO()` in schemas, `toDomain()` and static `fromDomain(...)` in JPA entities, static `from*` in responses and history entities (`fromEntity`, `fromOrganization`), `toHistoryData()` in domain entities; plus the static helpers of `common/` (`JsonHandlers.toJson`, `toSnakeCase`). Services, gateways, controllers and other components never have a `to*`/`from*` method: a private step that checks a value is `validate*` and returns nothing (e.g. `validateTokenResponse`), and one that builds something is named after the action (`fetch*`, `build*`).

## Transactions and repositories
- Explicit transaction control through the `UnitOfWork` (request-scoped `JpaUnitOfWork`), never `@Transactional`.
- Reads go **before** `unitOfWork.begin()`, validations first (e.g. duplicate checks) and only then the lookups the writes need (e.g. the PENDING status); `begin()`/`commit()` wraps only the writes.
- No manual rollback in services: the `JpaUnitOfWork` `cleanup()` rolls back at the end of the request.
- Repositories use only derived queries (no `@Query`/JPQL, no `@EntityGraph`); each repository returns the entity of its own table with `toDomain()` already assembling the relationships; the service uses what the domain loaded, without fetching the same entity again.
- Always take the simplest path: plain derived lookups in sequence (e.g. the person by key, then the collaborator by key and role), no custom queries, extra abstractions or redundant calls when a direct one solves it.
- `*RepositoryImpl` calls the plain `jpaRepository.save` (no `saveAndFlush`). With `AUTO_INCREMENT` the INSERT runs on `save`, inside the transaction.
- Existence checks use `findBy...().isPresent()`, never `existsBy...` methods.
- Relationships are `FetchType.LAZY`; `spring.jpa.open-in-view` stays at the Spring Boot default (enabled), so `toDomain()` can load them during the HTTP request even outside `begin()`/`commit()`. Non-HTTP entry points (Kafka consumers) must read lazy relationships inside a transaction. List routes keep it too: the page comes in a single query and each relationship loads lazily in `toDomain()`; the persistence context fetches each distinct related row once (type tables have few rows), so no `@EntityGraph`/`JOIN FETCH` for them. Revisit only when a relationship points to data that differs per item (e.g. each company's owner).
- `try/catch` only around the call that actually throws (e.g. the `save` hitting a `UNIQUE` → `DataIntegrityViolationException` becomes the domain duplicate exception).

## Errors
- Handlers take no `Locale` parameter; `build` reads the request language from `LocaleContextHolder.getLocale()` (fed by `Accept-Language`) to pick `messages.properties` or `messages_pt.properties`.
- Every error goes through `build` and answers `ErrorResponse(title, message, code, extra_fields)`; `extra_fields` is always present, an empty list when there is nothing to add. A schema validation failure (`MethodArgumentNotValidException`) answers 400 `GEN00400` with `extra_fields`: `ExtraFieldErrorResponse(field, error)` items where `field` is the JSON path in snake_case (e.g. `legal_person_collaborators[0].password`) and `error` is `REQUIRED` (`@NotBlank`, `@NotNull`), `INVALID_FORMAT` (`@Pattern`, `@Email`, `@Positive`, `@Digits`, and a value that does not parse, such as an unknown enum, which answers with `field` `body`) or `SIZE` (`@Size`, `@Min`, `@Max`). A violation on a `@RequestParam` (native method validation, `HandlerMethodValidationException`) answers 400 `GEN00400` with `[{"field": "page_size", "error": "SIZE"}]` (`ExtraFieldErrorResponse.fromParameterError`) and a parameter of the wrong type (`MethodArgumentTypeMismatchException`) answers `[{"field": "organization_status", "error": "INVALID_FORMAT"}]`. `GEN00400` always carries a non-empty `extra_fields`: an unreadable body (`HttpMessageNotReadableException`) answers `[{"field": "body", "error": "INVALID_FORMAT"}]`. No other error uses `GEN00400`. Passwords and tokens never appear in a log or a response. Logs never receive a DTO, schema, response or entity: only the single `Map` with the chosen fields, which never includes a password or a token; records do not override `toString`. Documents (CPF, CNPJ) and keys may be logged.
- Business exceptions extend `DomainException` (`getCode()`, `getMessageKey()`), mapped to an HTTP status in the `GlobalExceptionHandler` `STATUS_MAP`; response `ErrorResponse(title, message, code, extra_fields)` with the message from the `MessageSource` (`messages.properties` in English and `messages_pt.properties`).
- Never branch on types with `instanceof` (including pattern matching); write one method per type instead (e.g. one `@ExceptionHandler` per exception).
- Application setup errors (e.g. a domain table enumerator not found) throw a generic exception (`IllegalStateException`) → 500 `GEN00500`.
- Exception messages are plain literal text (e.g. `"Organization status PENDING not found"`), no string concatenation.
- Codes: generic errors (schema validation, authentication, permission, unknown route or method, unsupported media type and unexpected failures) use `GEN` + the HTTP status (`GEN00400`, `GEN00401`, `GEN00403`, `GEN00404`, `GEN00405`, `GEN00415`, `GEN00500`). Authentication and permission exceptions (e.g. `UnauthorizedInternalRequestException`) are generic too: they use `GEN00401` / `GEN00403` and map to 401 / 403. Every other `DomainException` carries the service code `<SVC>0000N` (e.g. `ORG00001`, `ONB00006`) and maps to a 4xx status in the `STATUS_MAP`. Every `DomainException` must be mapped: the 500 default of `getOrDefault` exists only for a forgotten mapping, which is a bug. 500 is always `GEN00500` with the generic `error.internal` message.

## API
- Dates and times in responses are `Instant`, serialized as ISO 8601 in UTC with `Z` (`"created_at": "2026-11-03T22:50:27.442Z"`), never `LocalDateTime`, which goes out without a zone and is read as local time by the clients. Entities keep `LocalDateTime` in UTC (the containers and MySQL run in UTC), and the response converts it in `from*` with `toInstant(ZoneOffset.UTC)`; integration tests assert that the value ends with `Z`.
- UUID fields are validated with `@UUID(allowNil = false, letterCase = UUID.LetterCase.INSENSITIVE)`.
- No nested records in schemas, DTOs or responses: each nested object is its own file. Nested input objects live in `definitions/` (`api/schemas/definitions`, `application/dtos/input/definitions`) with generic names, without the operation (e.g. `PersonPhoneNumberSchema`, `PersonPhoneNumberDTO`); create a specific variant only when the validations diverge.
- Schemas validate only the shape of the request (required fields, size, digits-only format, list size). Business rules (document check digits, allowed values such as the collaborator role) live in the service and throw domain exceptions, except an option backed by a closed list that only has to be sent back to a provider, such as the company type, which is a typed enum in the schema; no custom Bean Validation annotations.
- Route paths start with the service name (`/onboarding/legal_persons`), in snake_case with underscores, never hyphens. Internal routes live under `/<service>/internal/**` (e.g. `/organization/internal/organizations`). The gateways expose routes without the prefix and add it when forwarding; the `backoffice-gateway` exposes the internal routes as `/internal/**`, only to the admin; no other gateway exposes them.
- JSON in snake_case.
- Internal route (`/<service>/internal/**`): the controller takes `@RequestHeader(value = "internal-token", required = false)` and `@RequestHeader(value = "selected-user-roles", required = false)` and calls `internalRequestValidator.validateInternalTokenOrAdmin(internalToken, selectedUserRoles)` on its first line (no filter). It is valid when the token equals the configured one (shared by every application, `INTERNAL_TOKEN`, compared with `equals`) or when `selected-user-roles` (comma-separated, each item trimmed) contains `admin`; otherwise `UnauthorizedInternalRequestException` (401 `GEN00401`). Service-to-service calls use the token; the admin reaches the route through the `backoffice-gateway`, which sends `selected-user-roles`.
- Responses of internal routes are named `<Action>Internal<Resource>Response` (`GetInternalLegalPersonResponse`) and their output DTOs `<Action>Internal<Resource>DTO` (`GetInternalLegalPersonDTO`).
- Logs follow `ClassName.method - message`. The message is literal text; data goes in a single `Map` argument (`logger.error("X.y - Failed to create the user {}", Map.of("person_key", key), e)`), never interpolated in the sentence. The exception is passed as the last argument, never `e.getMessage()`.
- A create endpoint returns only the created resource (no child lists).
- List routes: each filter is a loose `@RequestParam`, plus `page` (default 1, `@Min(1)`) and `page_size` (default 30, `@Min(1) @Max(100)`) validated on the `@RequestParam` itself, a violation returning 400 `GEN00400` with the parameter name in `extra_fields`; the service calls `list<X>s(filters..., page, pageSize)` and returns `List<X>`. Filtering lives in `<X>Specification.withFilters(...)` (`infrastructure/jpa/specifications`, starts from `criteriaBuilder.conjunction()` and adds one `equal` per informed filter); `<X>RepositoryImpl.findAll(filters..., page, pageSize)` returns a `List` using `PageRequest.of(page - 1, pageSize)` and the `Jpa*Repository` extends `JpaSpecificationExecutor`. The response is `PaginatedResponse<List<X>sResponse>(data, PaginationResponse(page, page_size))` (generic, both in `api/responses/pagination/`), and the item is the route's `List<X>sResponse` in `api/responses/` (e.g. `PaginatedResponse<ListOrganizationsResponse>` in the organization-service); objects nested inside it go to `definitions/`.
- A list route resolved by the token reads `selected-agent-key` and always filters by it. The `selected-*` headers a route needs are read with `required = false` and validated by the `InternalRequestValidator` (`validateSelectedAgentKey`; absent or blank → 401 `GEN00401`, `MissingSelectedAgentKeyException`), never with Bean Validation or a required header. An item fetched by its own key returns the object or 404; with `selected-agent-key`, a key different from the token's also answers 404 (same `<X>NotFoundException`, never revealing the existence).

## External gateways
- Each gateway has its own folder in `domain/gateways/<gateway>/` (named after the gateway, not the provider), holding the interface and a `dtos/` folder (e.g. `identityprovider/IdentityProviderGateway`, `identityprovider/dtos/CreateUserInputDTO`). The interface receives and returns those DTOs, named after the operation, never loose parameters.
- The implementation lives in `infrastructure/gateways/<provider>/` named `<Provider><Interface>` (e.g. `keycloak/KeycloakIdentityProviderGateway`, `organizationservice/OrganizationServiceOrganizationGateway`), using `RestClient`. Request and response bodies are typed records in `infrastructure/gateways/<provider>/dtos` (`<Provider><Operation>Request` / `Response`) with `@JsonProperty` on every field; no `Map` bodies.
- Timeouts come from `spring.http.clients.connect-timeout` and `spring.http.clients.read-timeout`, which Spring Boot applies to the auto-configured `RestClient.Builder`; gateways receive the builder injected and never build a request factory by hand.
- The base URL comes from the property `app.<name>.url`, fed by the `<NAME>_URL` variable that `service-start.sh` resolves from the `<NAME>_TEST_URL` / `<NAME>_DEVELOPMENT_URL` pair.
- A transport failure or unexpected status in the operation itself is logged in the gateway and becomes a domain exception for the operation (e.g. `UserCreationException`), mapped to 422 in the `STATUS_MAP`, never to a 5xx: a 5xx is only the generic `GEN00500` for unexpected failures, with the service code and a generic "try again later" message. Each `try` wraps only the HTTP call (one `try` per call); status and body checks come after it. The access token is part of the operation: its failure (transport, error status or no token in the body) is logged and becomes the same domain exception (e.g. `UserCreationException`). Other auxiliary calls (lookups such as the role) run before the operation, outside its `try`, and fail with a generic exception (`IllegalStateException` or the `RestClientException` itself) → 500 `GEN00500`.
- `GET /onboarding/auth/me` answers who is logged in from headers the backoffice gateway takes from the already validated token: `selected-user-key` (the `person_key` of the person, required), `selected-agent-key` (the `legal_person_key` of the organizer's company, optional: absent for the admin) and `selected-user-roles` (realm roles separated by commas, required, split without filtering). The service returns `GetSessionDTO` and the response is `GetSessionResponse` (`fromDTO`) `{person_key, name, document_number, roles, legal_person}` with `legal_person` (`SessionLegalPersonResponse`) as `{legal_person_key, name}` or `null` (still present in the JSON) when there is no agent key. A person that does not exist, an agent key that matches no company, or a person who is not a collaborator of that company (`LegalPersonCollaboratorRepository.existsByLegalPersonKeyAndNaturalPersonKey`, checked in this order and regardless of the collaborator status, each failure with a `warn` log carrying `person_key` and `legal_person_key`) throws `InvalidSessionException` → 401 `GEN00401` (`error.invalid_session`, generic authentication error like the others); a missing required header is handled by `handleMissingHeader` → 400 `GEN00400` with `extra_fields` `[{"field": "<header-name>", "error": "REQUIRED"}]` (the header name as sent, not snake_case). `findByPersonKey` on `LegalPersonRepository` receives the `person_key` of the legal person, which is the `legal_person_key`.
- Input DTOs (`application/dtos/input`) exist only for fields that come from the request body through a schema; header, path and query values are passed to the service as plain parameters (e.g. `getSession(String personKey, String legalPersonKey, String roles)`).
- The `OutputDTO` suffix (and `from*Output` in responses) is only for what an external gateway returns; service outputs that do not come from a gateway are `<Action><Resource>DTO` in `application/dtos/output`, named after the response they build with the suffix swapped (`GetLegalPersonDTO` → `GetLegalPersonResponse`, `GetSessionDTO` → `GetSessionResponse`), and the response uses `fromDTO`.
- Top-level responses in `api/responses/` are named `<Action><Resource>Response` (`CreateLegalPersonResponse`, `GetLegalPersonResponse`, `CreateSessionResponse`, reused by refresh); nested objects in `definitions/` take only the resource name (`LegalPersonOwnerResponse`); pagination lives in `api/responses/pagination/`.
- Reusable nested responses live in `api/responses/definitions/` as `<Entity>Response` with `fromEntity`.
- Authentication routes (`/onboarding/auth/login`, `/refresh`, `/logout`) only relay the identity provider session: the tokens issued by Keycloak go back untouched in `CreateSessionResponse`, and `invalid_grant` becomes 401 `GEN00401` (`InvalidCredentialsException` on login, `InvalidRefreshTokenException` on refresh and logout). The realm revokes the refresh token on every renewal (`revokeRefreshToken`, `refreshTokenMaxReuse` 0): each refresh returns a new refresh token, a used one is refused with `invalid_grant` and Keycloak then ends the whole session, so the new token of that renewal is refused too. The service just relays this; it never caches or retries a refresh token. Tokens and passwords never appear in a log (see Errors); the CPF may be logged. Reading the error status of the token endpoint uses `onStatus` with an empty handler so the status and body checks come after the single `try` around the call.
- Each public operation of a gateway makes its own main HTTP call inline (request, `try`, status checks), even when that duplicates code across operations (e.g. `createSession` and `refreshSession` both call the token endpoint). Private methods are only for auxiliary steps that are not the operation itself (`fetchAccessToken`, `fetchRole`, small predicates such as `isInvalidGrant`, and the checks of a response body shared by several operations, such as `validateTokenResponse`, which only validates and returns nothing; the mapping to the output DTO stays inline in each operation). `to*` names are reserved for conversions of the object itself (`toDTO`, `toDomain`) and static helpers (`toJson`), never for a private step that validates. This keeps the new-code duplication below the 3% of the SonarQube quality gate.
